# Chrome extension authentication

Capture will use Supabase Auth's OAuth 2.1 authorization-code flow with PKCE (Proof Key for Code Exchange). The Chrome extension is a registered public client, and the Capture website continues to handle sign-in and consent with the same Supabase user. The extension runs the standard OAuth requests against the project's Auth endpoints. [Supabase setup](https://supabase.com/docs/guides/auth/oauth-server/getting-started) · [OAuth flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows)

## Environment configuration

Each environment pairs its Capture web origin with one Supabase Auth issuer, a public OAuth client ID, and a stable Chrome extension ID. A deployment operator registers that client with token endpoint authentication set to `none` and one redirect URI. The registered URI must equal the result of `chrome.identity.getRedirectURL("capture-auth")`, which has the form `https://<extension-id>.chromiumapp.org/capture-auth`. Keep dynamic client registration disabled. A development build needs a stable unpacked ID, and staging and production register their own IDs and clients. Use HTTPS for hosted web and Auth endpoints. The loopback web origin is a development exception. [Chrome Identity](https://developer.chrome.com/docs/extensions/reference/api/identity) · [Supabase client registration](https://supabase.com/docs/guides/auth/oauth-server/getting-started#register-an-oauth-client)

Enable the hosted OAuth server only after the consent handler and API and database authorization controls are deployed. Configure `/oauth/consent` as the authorization path and verify the project's discovery document and endpoints at deployment. Confirm the deployed Auth release enforces the OAuth client boundary on account-management operations before connecting real accounts. The bundle contains public identifiers and endpoint configuration. Deployment credentials, database secret keys, signing keys, and OAuth client secrets are excluded. [Supabase Auth account route policy](https://github.com/supabase/auth/blob/master/internal/api/api.go)

## Connect and exchange

1. The user selects **Connect Capture** in the popup. The Manifest V3 worker generates independent random values for `state` and the PKCE verifier using Web Crypto (32 bytes each, base64url-encoded). The challenge is the base64url-encoded SHA-256 digest of the verifier. The worker keeps a single pending attempt in trusted-only `chrome.storage.session`, including its creation time and pinned callback. The attempt expires after 10 minutes and is discarded on cancellation, replacement, or completion. A storage or configuration failure stops the flow.
2. The worker starts `chrome.identity.launchWebAuthFlow` in interactive mode from that user gesture. The pinned Supabase `/auth/v1/oauth/authorize` request uses `response_type=code`, the client ID, the exact redirect URI, `code_challenge_method=S256`, the challenge, `state`, and `scope=email`. Capture obtains account identity through its API. The scope controls provider identity metadata and does not enforce Capture's data permissions.
3. Supabase directs the user to Capture's consent page with an opaque `authorization_id`. The web app gets authorization details from Supabase with the signed-in web session. If sign-in is needed, the return destination is the fixed `/oauth/consent` path plus the validated, bounded ID. The consent action checks the authenticated user, the same web origin, and the provider-confirmed registered client and callback before issuing a decision. Every resulting redirect, including one for an existing grant, must have exactly the registered callback origin and path. The page explains the extension's access and allows approval or denial. Credential-free error copy and a failure response handle missing or invalid consent data.
4. Chrome returns the callback to the worker. The worker compares the URL without its query to the exact registered URI, rejecting credentials and fragments. It requires one `state` matching the unexpired pending attempt and a single `code` for success. Any error result ends the attempt, and its provider-supplied description stays out of the UI and logs. Duplicate or unexpected parameters, simultaneous `code` and `error`, and cancellation end the attempt. The worker consumes the pending attempt before exchanging the code. A new attempt is required after a failed exchange. State binds the callback to this connection attempt, while PKCE binds the short-lived, single-use provider code to its verifier.
5. The worker sends a form-encoded `POST` to the pinned Supabase `/auth/v1/oauth/token` with `grant_type=authorization_code`, `client_id`, `redirect_uri`, `code`, and `code_verifier`. It omits browser cookies and rejects fetch redirects. It accepts only a valid bearer token response with access and refresh tokens and expiry, then calls Capture's `GET /api/me` to verify the account before presenting a connected state. Access and refresh tokens travel in headers or bodies over HTTPS, with the loopback exception reserved for development fixtures. Error reporting and telemetry redact token-endpoint bodies, consent IDs, callback URLs, codes, state, verifiers, and credentials. The consent page uses `Cache-Control: no-store` and a no-referrer policy. [Chrome Identity](https://developer.chrome.com/docs/extensions/reference/api/identity) · [Supabase OAuth flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows)

## API and extension boundaries

- The worker owns the token exchange, storage, and authenticated API requests. The popup receives connection status, account display data, and capture results. The worker accepts only explicit internal commands from its own popup document, checked against its extension ID and exact popup URL. Content scripts and page code receive no credentials. The manifest omits `externally_connectable`; there are no external message listeners or `window.postMessage` bridges for authentication.
- Keep extension host permissions to the configured Capture and Supabase origins. Fetch Capture endpoints with `Authorization: Bearer <access_token>`, `credentials: "omit"`, and redirects disabled. Requests use fixed endpoint paths. On `/api/me` and `/api/captures`, allow CORS only for the exact configured `chrome-extension://<extension-id>` origin, with `Vary: Origin`, route-specific methods, and the necessary authorization and content-type headers. Decline unapproved cross-origin requests and omit credentialed CORS. Verify actual Origin header behavior in Chrome. CORS is a browser restriction. The bearer and session checks are required even when a caller omits or supplies an Origin header. [Chrome cross-origin requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)
- For OAuth bearer requests, Capture verifies signature, issuer, audience, expiry, the authenticated user ID, the registered `client_id`, and a live `session_id` for that user and client. Use the project's published signing keys and the server-side session check for the bearer path. Preserve the existing web session path for web users. The extension can read its minimal account details and submit captures. Other routes reject OAuth-client credentials by default. Owner and rate checks continue to run at the database boundary.
- Supabase standard OAuth scopes do not restrict access to PostgREST or RPCs. Before enabling the client, enforce that boundary in the database too. Restrictive policies block OAuth-client JWTs from ordinary authenticated tables, and general-purpose authenticated RPCs reject them. The narrow account lookup and capture operations can use reviewed owner-scoped RPCs. Those operations require the approved client and live session, derive the owner from the token, and expose only the required data or action. The existing capture save already checks the session; it needs the approved-client rule before OAuth is enabled. [Supabase OAuth token security](https://supabase.com/docs/guides/auth/oauth-server/token-security) · [Supabase user sessions](https://supabase.com/docs/guides/auth/sessions)

## Storage, refresh, and disconnect

- Restrict `chrome.storage.local` to `TRUSTED_CONTEXTS` before persisting or reading credentials. The worker stores the access token, refresh token, expiry, and environment association together. The popup uses messages for account state, without reading credentials. Tokens stay out of synced storage, website storage, and page context. Pending PKCE material stays in trusted session storage and is cleared when the attempt ends. The connection survives a worker restart. [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage)
- Refresh near expiry or on the first Capture API `401`. The worker serializes refreshes and sends a form-encoded `POST` to the same token endpoint with `grant_type=refresh_token`, `refresh_token`, and `client_id`. It atomically replaces the stored session record, retaining the previous refresh token only if the successful provider response omits a replacement. The worker retries the original request at most once after refreshing, reusing the original capture request ID. A terminal refresh failure or a second `401` clears the local session and asks the user to reconnect. Timeouts or temporary service errors produce a retryable state. Disconnect and account changes invalidate in-flight work so delayed responses cannot restore a cleared connection.
- **Disconnect** stops extension requests and clears local credentials immediately. It opens a fixed Capture account page where the user can confirm **Revoke extension access** in their normal web session. The web action revokes the OAuth grant for the registered client, ending all extension sessions for that client on the account. The popup reports local disconnect only. The web page reports whether remote revocation succeeded. Ordinary web sign-out is scoped to the web session. On each authenticated extension request, Capture checks the live session so an access token from a revoked session cannot continue working until expiry. [Supabase signOut](https://supabase.com/docs/reference/javascript/auth-signout) · [Supabase grant revocation](https://supabase.com/docs/reference/javascript/oauth-server-revokegrant)

## Threat-model review

| Threat                                                                         | Required control and expected outcome                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An attacker changes the destination or supplies a different extension ID       | Supabase requires the registered callback URI. Capture verifies the consent redirect, and the worker requires the exact pinned callback. No token endpoint or callback can be selected by page content.                |
| A callback is unsolicited, expired, repeated, or stolen                        | A mismatched, expired, or consumed state stops the client. A stolen code cannot be exchanged without the verifier, and Supabase accepts a valid code only once.                                                        |
| Credentials leak through URLs, browser history, or diagnostics                 | URLs carry only public OAuth parameters and short-lived handoff values. Access tokens, refresh tokens, and the verifier stay out of URLs. The worker rejects network redirects and credentials are redacted from logs. |
| An arbitrary web page or content script tries to control the extension         | There are no external auth messages. The worker validates the sender and command before acting. Page context cannot read trusted credential storage.                                                                   |
| A browser origin or OAuth client is substituted                                | The API allowlists the extension origin for CORS and separately verifies the token's issuer, client, owner, and live session. A caller cannot authorize itself by supplying an Origin header.                          |
| A valid extension token reaches the data API or another Capture route          | Extension-specific access is limited at both the web and database boundaries. The allowed capture operation applies the same ownership and request limits as the web flow.                                             |
| An old token survives revocation, or an in-flight refresh resurrects a session | The API and allowed RPCs require a live provider session. The worker guards credential writes against changes in the connected session.                                                                                |

CAP-040 verifies the contract by reviewing the handoffs, credential locations, and trust boundaries against the provider and Chrome specifications and the current API. CAP-041 must prove connect, account identity, rotation, and revocation with disposable accounts, and verify the hosted Auth release's account-management boundary before real use. CAP-047 and CAP-048 must verify the built manifest, browser-origin behavior, and isolation from arbitrary pages and content scripts. Enable real-account access only after the environment passes its runtime checks.
